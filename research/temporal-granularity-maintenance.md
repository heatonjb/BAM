# Temporal Granularity, Schema Evolution, and the Maintenance Economics of a Business Graph

A business modelled as a transformation machine is a graph whose edges carry time. Assets and liabilities are nodes; transformations are edges whose truth depends on *when* you ask. The moment an edge is timestamped, three questions appear at once: which clocks to record, how the shape of that record may change, and whether the cost of keeping history is worth the decisions it supports. This document covers temporal modelling practice, schema evolution on a versioned graph, the economics of history retention, a granularity decision procedure, and the failure evidence of what actually breaks.

## 1. Temporal Modelling Practice

### 1.1 The two orthogonal clocks

The foundational distinction comes from the temporal-database literature. Snodgrass defines *valid time* as "the time a fact was true in reality" and *transaction time* as "the time the fact was present in the database as stored data," noting the two "are orthogonal" though "there are generally some application dependent correlations between the two times" [T1, *Temporal Databases* (Snodgrass), §2.2 "Dimensionality", para. 2]. A model supporting both is *bitemporal*; supporting only valid time is *historical*; only transaction time is *rollback*; neither is *snapshot* [T1, same, §2.2, para. 2]. Because transaction time is monotonic and append-only, bitemporal relations "are append-only, making them prime candidates for storage on write-once optical disks" [T1, same, §2.2, para. 4].

Martin Fowler renamed the pair *actual* and *record* history because practitioners found "valid/transaction" confusing, but the semantics match Snodgrass and the SQL standard [T2, Fowler, *Bitemporal History*, §1 "Actual/record versus valid/transaction"]. The key discipline: if you use event sourcing for bitemporal history, "each event needs an actual date (or time) for when the event occurred in the world, and a record date (or time) for when we learned about it" [T2, Fowler, same, main body, para. 2].

SQL:2011 standardised this. System-versioned tables use `PERIOD FOR SYSTEM_TIME` with `WITH SYSTEM VERSIONING`; application-time tables use a user-named period; both together yield bitemporal tables [T1, Kulkarni & Michels, *Temporal features in SQL:2011*, SIGMOD Record, "system-versioned tables" discussion; T2, Wikipedia, *SQL:2011*, "Temporal databases"]. Its advantage over a bespoke period type is that databases storing periods as datetime column pairs can adopt it incrementally, and Microsoft SQL Server 2016, IBM DB2 10, MariaDB 10.3/10.4, and SAP HANA 2.0 all implemented variants [T1, Kulkarni & Michels, same, para. 1; T2, Wikipedia, same]. Microsoft's docs confirm the engine auto-maintains period columns and that all rows inserted in one transaction share the same system-start time [T2, Microsoft Learn, *Temporal tables overview*, "system-versioning" section].

### 1.2 Event time versus processing time

The same split appears operationally as event-time vs processing-time in change data capture. Debezium frames the choice between two sources of truth: "Event Sourcing uses its own journal as the source of truth, while Change Data Capture depends on the underlying database transaction log as the source of truth" [T2, Debezium blog, *Event Sourcing vs CDC*, "Introduction", para. 3]. Every event therefore carries a business timestamp (when it happened) and an ingestion timestamp (when the pipeline saw it); collapsing them loses the ability to answer "what did we know when."

### 1.3 Slowly changing dimensions

Kimball's slowly changing dimension (SCD) taxonomy is the most widely deployed temporal pattern in analytics. In "30 years of studying this issue," Kimball found "only three different kinds of responses are needed": Type 1 (overwrite), Type 2 (add a row), Type 3 (add a column) [T2, Kimball Group, *Slowly Changing Dimensions, Part 2*, "Type 2" section]. Type 2 requires a surrogate key and five administrative fields including effective-dated begin/end and a current flag, with the invariant that "the end-effective-datetime of a Type 2 dimension record must be exactly equal to the begin-effective-datetime of the next change" [T2, Kimball Group, same]. Later hybrid types (4, 5, 6, 7) emerged, with Type 6 embedding current values as overwritten Type 1 columns inside a Type 2 row [T2, Kimball Group, *Design Tip #152*].

Type 2 dominates because it is the only pattern that "allows us to make good on the data warehouse pledge to preserve history faithfully" [T2, Kimball Group, *Slowly Changing Dimensions, Part 2*, "Type 2"]. But its failure modes are sharp and well documented. The most common catastrophic error is joining facts on the business key rather than the surrogate key, which "collapses all history into the current row" [T2, Data Warehouse Info, *Slowly changing dimensions: implementation strategies*, "SCD Type 2" section]. A second failure is flag-only identification: a late-arriving fact "will be incorrectly joined to the current row rather than the row that was active at the event timestamp," producing "systematically wrong history" [T2, same]. A widely cited Stack Overflow case describes retroactive corrections requiring an "expensive update operation over a number of enormous tables" of 10M–200M rows, with row-splitting risking date-range overlap [T3, Stack Overflow, *How to best handle historical data changes in an SCD2*]. Type 2's growth cost is direct: "every changed attribute generates a new row, the dimension grows roughly with the rate of change, and every fact load pays the range-join cost" [T2, datamodelassistant.com, *SCD Type 2 Implementation*, "half-open interval" section].

### 1.4 Data Vault 2.0

Data Vault 2.0 encodes the two clocks as Load Date (technical) and Effective From (business), and the practitioner community is explicit that a source delivering a "complete, retroactively mutable business timeline" is "fundamentally a bitemporal problem" that must be preserved without overwriting what was loaded at T1 [T2, Data Community Forum, *Handling Retroactive Changes to Historical Effectivity in Data Vault 2.0*, accepted-answer thread]. Effectivity Satellites track relationship validity via a driving key, but the standard warns they are "not the same as SCD2" and are exclusively for temporal relevance of a relationship, not attribute history [T2, DV2.org, *Data Vault Anti-pattern: Using Effectivity Satellites as SCD2*]. The maintenance-heavy artifact is the temporal PIT (T-PIT): "whenever valid_from or valid_to dates change, you may need to rebuild PIT partitions — which can be expensive if large date ranges are altered" [T2, Scalefree, *Joining SCD2 Tables Using Data Vault*, "T-PIT" section]. The recommended posture is to push business-timeline interpretation "as far downstream as possible" to keep maintenance cheap [T2, same].

### 1.5 Event sourcing

Event sourcing makes the log the source of truth. A constructivist-grounded-theory study of 19 industrial event-sourced systems identified five recurring challenges: "event system evolution, the steep learning curve, lack of available technology, rebuilding projections, and data privacy" [T1, Overeem, Spoor & Jansen, *The Journal of Systems & Software* 178 (2021) 110970, Abstract]. For the evolution challenge it catalogued five tactics — "versioned events, weak schema, upcasting, in-place transformation, and copy-and-transform" — and advised systems "start out using versioned events and weak schema, while later evolving to upcasting and even copy-and-transform techniques" [T1, same, Abstract and §7].

### 1.6 CDC, Debezium, and the outbox

Operationally, the outbox pattern plus CDC is the mainstream way to derive a time-ordered stream without dual writes. Debezium's own guidance is blunt: CDC + Outbox "avoids the Dual Writes flaw, and is generally a more practical solution" than event sourcing for the average team, because "the source of truth stays within the application database tables and transaction log" [T2, Debezium blog, *Event Sourcing vs CDC*, "Pros for CDC + Outbox" list, items 1 and 4]. The pattern gives at-least-once delivery, not exactly-once, so consumers must be idempotent [T2, Baremon, *Kafka and Databases: CDC, Debezium and the Outbox Pattern*, "Important boundary" note]. A production field report gives concrete thresholds: Debezium lag should stay under 5 seconds (green), 5–30 seconds investigate, over 30 seconds an incident, with alerts on replication-slot lag above 10 MB and outbox tables above 100k rows [T3, Florian Courouge, *PostgreSQL Outbox*, "Production Metrics to Monitor"].

### 1.7 Effective-dated audits and point-in-time reconstruction

Point-in-time (PIT) data means answering two questions: "When was the information known? and What information was known at that time?" [T1, S&P Global Market Intelligence, *Point in Time vs. Lagged Fundamentals* (S&P Capital IQ), para. 1]. PIT stamps each observation with its filing/announcement date; non-PIT databases "typically overwrite historical data with data that was later changed or corrected," destroying the original record [T1, same, para. 2]. Reconstruction requires version identity (original filing → amendment → restatement → recast) and a query of the form "find the latest valid observation whose supported availability is no later than time T" [T2, SourceState, *Point-in-Time Financial Data*, "What a point-in-time financial record needs" section].

## 2. Schema Evolution and Versioning

### 2.1 Serialization formats and the registry

Schema registries enforce compatibility before accepting a new version. The standard levels: *backward* (new consumers read old data), *forward* (old consumers read new data), *full* (both), and their *transitive* variants that check against all prior versions, not just the last [T2, Confluent Docs, *Schema Evolution & Compatibility Types*, "compatibility types" bullet list]. The default is `BACKWARD`, chosen so consumers "can rewind to the beginning of the topic" [T2, same, "Backward compatibility" section]. Concretely, for Avro and Protobuf, adding or removing an *optional* field is fully compatible; adding a required field is forward-compatible only; widening a scalar type is backward-compatible for Avro but both for Protobuf [T2, same, "Avro and Protobuf compatibility" table]. Best practice for Protobuf is `BACKWARD_TRANSITIVE`, because "adding new message types is not forward compatible" [T2, same, "Best practice" note]. JSON Schema rules are more involved still [T2, same, "Avro, Protobuf, and JSON Schema have different compatibility rules"].

### 2.2 Event and aggregate schema evolution

Once events are immutable, schema evolution becomes forward-only. The single most dangerous change is a field rename: under weak schema "a rename is a delete plus an add," and the mapper "silently hands every historical event the default value instead of the real data. No error. No crash. Just quietly wrong state on replay" [T3, Andrii Boyko, *The Genuinely Hard Parts of Event Sourcing in Production*, "schema evolution" section]. The remedy is upcasting: a read-time pure function that promotes an old event shape to the current one, with the schema number stored alongside the event so the upcaster is "a lookup, not a guess" [T3, same]. Upcasters chain v1→v2→v3, but an upcaster "can add information but it cannot invent it" — if v1 never recorded a field, no transform recovers it [T3, same].

### 2.3 Graph schema migration

Graph databases are schema-optional, which makes drift *easier* and therefore more dangerous. The discipline is identical to relational expand-contract: "You never mutate the old structure in place; you stand up the new structure alongside it, keep both populated during a transition window, verify the new shape against real consumers, and only then decommission the legacy structure" [T3, Graph Data Modeling, *Schema Evolution and Versioning*]. Four invariants are named: version the schema manifest under semantic versioning; additive before destructive; every migration step idempotent and re-runnable; and the destructive step gated on "a consumer verification query — not a timer" [T3, same]. A pure graph hazard: encoding version as a runtime-generated label "fragments the planner's per-label histograms and defeats plan caching" [T3, same]. Neo4j's modelling docs lay out four temporal patterns — entity versioning, time-based versioning with `validFrom`/`validTo`, linked lists, and timeline trees — and concede the trade-off: time-based versioning gives "complete history" but "duplications of data cannot be avoided" [T2, Neo4j Docs, *Versioning*]. Academic work has even proposed a graph evolution language adding a `transform` operator, noting "there currently is no graph database system that implements schema evolution with complex refactoring operations" [T1, Hausler et al., *A language for graph database evolution*, CEUR-WS Vol-3618, Abstract and §5.7].

### 2.4 The cost and failure modes of schema churn

Schema churn compounds. A field-cited case: "metafield schemas designed in the first sprint and never revisited" that made sense at 50 SKUs but not 5,000, where "migrating metafields on a live store without breaking storefronts, third-party tools, and automations is miserable work" [T3, brainiac.studio, *The Shopify architecture decisions we actually regret*, "Third" item]. The remedy adopted was to "treat the metafield schema as a proper data model with a review gate before every new addition, and document deprecation paths from day one" [T3, same]. At the engineering level, a large-scale empirical study of 102 data-intensive systems found data-access self-admitted technical debt had a median survival of 1,000 commits (~2.9 years in SQL systems), with 5% of such comments introduced in the very first version and 68% of those persisting to the latest version [T1, *FIXME: Synchronize with Database* (arXiv:2201.02180), "survival analysis" results]. Schema and data-access decisions are the slowest-decaying debt.

## 3. Maintenance Economics

### 3.1 Storage and compute cost of retaining history

History retention has a clear price floor. Cloud warehouses cluster at roughly $20–$23 per TB per month for active storage, dropping to $10–$20 per TB per month in archival tiers, with BigQuery at $10/TB/month after 90 days of inactivity [T3, Dataworkers, *Data Warehouse Cost Comparison 2026*, "Storage Costs" section; T3, StackCompare, *Snowflake vs BigQuery vs Redshift 2026*, "Storage Pricing"]. But the raw per-TB rate is a distraction: storage is "roughly five percent of a typical Databricks bill" and only 5–15% of total warehouse spend, while compute dominates [T3, LLBBL Blog, *The Real Cost of Your Data Lake*; T3, Dataworkers, same]. The retention multiplier surprises teams: Snowflake's immutable micro-partitions mean "a 1 TB table that's getting updated multiple times a day can balloon to 25 TB of billed storage" once Time Travel (up to 90 days) and the non-disableable 7-day Fail-Safe are counted [T3, LLBBL Blog, same]. And "30–40% of stored tables are unused — not queried in 90+ days," accumulating both cost and governance drag [T3, Dataworkers, same].

### 3.2 Reconstruction latency

Rebuilding state from a log scales linearly with event count: published curves put 1,000 events at ~100 ms, 10,000 at ~1 s, and 100,000 at ~10 s [T3, ZeroAlloc EventSourcing, *Replay and Rebuilding*, timing table]. The rule of thumb is not to snapshot until hot-aggregate replay is measurably over ~100 ms, then derive the interval from measurement: at a 0.3 ms p95 apply cost, 5,000 events costs ~1,500 ms per load without a snapshot versus ~15 ms at a snapshot-every-50 cadence [T3, DEV Community, *Event Sourcing Snapshots*, "replay cost math" and cadence sections]. Snapshots are caches, not facts: they "must always be able to delete every snapshot you own and rebuild them from the events," or you have accidentally made the snapshot the source of truth [T3, Boyko, *The Genuinely Hard Parts of Event Sourcing*, "snapshots" section].

### 3.3 Cost of schema change

A backward-incompatible schema change costs multiple deploys. A column rename done safely is "three separate deployments" (expand → migrate → contract) [T3, Suheb Ghare, *Zero-Downtime Database Migrations*, "Dangerous Migration: Renaming a Column"]. At scale, "the Expand/Contract discipline itself became the bottleneck rather than the database," with a single feature becoming "a three-week, multi-release orchestration effort" across ~40 microservices [T3, Pipeline & Prompts, *Database Migrations During Zero-Downtime Deploys*, "repeat incident" section]. That coordination cost is exactly why teams under deadline pressure skip phases and reintroduce incidents.

### 3.4 Operational burden and data debt

The operational surface of a temporal graph is people-heavy: analysts estimate data work is 40–60% people, 15–25% tooling, with compute the small visible line item [T3, Dataworkers, *Data Warehouse Cost Comparison 2026*]. The cost of *bad* data is measured: Gartner's benchmark puts poor data quality at $12.9M per large enterprise per year, scaled to ~$4,912 per employee and $617B annually across the US economy [T2, DoubleTrack, *The Hidden Cost of Dirty Data*, citing Gartner MQ 2020; T2, IDC, *Data Technical Debt* eBook]. IDC frames the mechanism: "the value of data starts to diminish as soon as you store it," and "data hoarding only exacerbates the challenge of rogue data, as it becomes exponentially more difficult to maintain, clean, and manage data that constantly grows" [T2, IDC, same]. A CMU SEI case study found teams bypassing an authoritative warehouse because of a 48-hour lag, spawning nightly copy jobs that "caused an explosion in data-storage usage" and made "authoritative data sources unclear" [T2, CMU SEI, *What Is Enterprise Technical Debt?*].

## 4. The Granularity Spectrum and How to Choose

Granularity is the resolution at which the graph records a fact. Three points on the spectrum dominate:

- **Per-transaction / per-event** (finest): one node or edge per business event (order, hire, meter reading). Maximum fidelity; highest write volume, longest reconstruction, most schema surface.
- **Per-period / per-snapshot** (coarser): one edge per entity per day/week/quarter (the "row-per-employee-per-day" pattern that turns a 100,000-row dimension into 20M rows) [T3, Stack Overflow, *How to best handle historical data changes in an SCD2*].
- **Per-decision / per-state-transition** (variable): a new edge only when a value that a decision actually depends on changes — the SCD2 change-detection rule, where you "hash the tracked columns and only close when the hash changes" [T2, datamodelassistant.com, *SCD Type 2 Implementation*, "Closing rows by date alone" warning].

The organizing principle is Fowler's: bitemporal record-keeping is what makes "as it actually was" separable from "as it was recorded" [T2, Fowler, *Bitemporal History*]. A decision-support graph needs enough temporal resolution that every input a decision consumed is reconstructable at the decision's clock, and no more. Over-granularity is not caution; it is cost — storage multipliers (Snowflake's 25× update amplification), linear replay growth, and a larger schema surface that each raise the odds of a rename landmine or a data-quality incident.

**A decision procedure.** For each fact type, ask, in order:

1. **Is the fact ever used to make a decision whose merit is judged later?** If no report or model ever filters by this attribute *as it was at the time*, use Type 1 overwrite and stop. "If no, save yourself the operational complexity" [T2, datamodelassistant.com, same, final test].
2. **What is the narrowest edge that still resolves the decision?** If the decision depends on an attribute *at the moment of a fact*, you need Type 2 / valid-time edges. If it only depends on current state, you need a current flag, not history.
3. **Which clock must be preserved?** If the decision must be reproducible *as originally available* (audit, regulators, backtests), you need **transaction time** (SQL:2011 system versioning; append-only). If it merely needs the real-world timeline (MECE over business time), **valid time** suffices. If both matter, keep both clocks — otherwise you cannot tell a correction from a change.
4. **Does the fact change frequently and get read rarely?** Prefer per-decision change edges and a derived current view over per-period materialisation.
5. **Does the fact have many events and get read hot?** Introduce snapshots only after measured replay exceeds ~100 ms, and set cadence to a target p95 rebuild time, not a fixed N [T3, DEV Community, *Event Sourcing Snapshots*].
6. **Will this shape survive a rename?** If not, model the value as a loosely-typed or versioned payload and plan an upcaster before the first write [T1, Overeem et al., 2021].

The heuristic in one line: **record at the coarsest clock that still lets you reconstruct every input of every decision you will need to defend, and prefer additive, forward-only schema evolution from day one.**

## 5. Case Evidence: What Actually Goes Wrong, and What Holds

### 5.1 Point-in-time reporting recalls and restatements

Financial restatement is the canonical temporal failure. Across developed-market companies, "78% have restated their audited, annual total revenues at least once within the following 400 days," and "static lagging mechanisms ... are not capable [of] replicating the analytical results derived from Point In Time models" [T1, S&P Global, *PIT vs. Lagged Fundamentals*, "Restatements" section and conclusion]. A 25-year review of 18,797 restatements by 10,581 firms found annual restatements peaked at 1,935 in 2006 and fell to 300 by 2020, with a 2020 average net-income impact of −$17.6M [T1, *Financial restatements spanning 1995 through 2020*, JAF, Table 1; T1, Audit Analytics, *2020 Financial Restatements*]. Roughly 3% of restatements involve fraud, and restating firms "were less likely to be profitable for the next three years" [T1, CAQ, *What ten years of restatement trends tell us*]. The lesson: overwrite prior values and you lose the ability to explain what a decision-maker actually saw — a non-PIT database "obscures accounting fraud," whereas PIT retains Enron's original fraudulent figures to this day [T1, S&P Global, same].

### 5.2 Event sourcing and CDC post-mortems

A production account of migrating a live system to event sourcing shows the transition cost: the initial checkpoint infrastructure was "about 7,000 lines ... a monument to premature abstraction," and keeping old and new behaviour identical during dual-write took longer than writing the new code [T3, LangWatch, *Four Refactors and a Funeral*]. A subtler temporal bug surfaced when fold projections read stale state: "reads could hit a node that hadn't replicated the previous write yet. Stale read, apply event on top of empty state, store that. Silently losing every field set by earlier events" [T3, LangWatch, same] — a processing-time/event-time race. On the CDC side, the dominant failure is assuming reliability removes the need for idempotency: "teams who implement the outbox write correctly but forget about idempotency on the consumer side ... during a deploy, Debezium restarts and replays events ... the billing service is confused" [T3, CloudRPS, *Transactional Outbox Pattern*].

### 5.3 Schema-migration incidents

Three public incidents show the same lock-shaped failure. GoCardless took ~15 seconds of downtime because adding a foreign key "takes AccessExclusive locks on both the table ... and the one it references," so an unrelated long-running read queued the whole API behind the migration [T3, GoCardless, *Zero-downtime Postgres migrations*]. Railway had *two* outages six weeks apart — 52 minutes on a billion-row non-`CONCURRENTLY` index, then 8 minutes on metadata-only "nullable column added" DDL that queued behind an `ACCESS SHARE` reader and drained PgBouncer [T3, DataPace, *Railway's two migration outages*]. A Laravel `->change()` ran sub-second on staging but eleven minutes on production's multi-million-row table, and "neither the tests nor staging could tell the reviewer how long it would take against production's actual data volume" [T3, Memet Zx, *A CI/CD Mistake That Shipped a Broken Migration*]. The defences that held: `lock_timeout` on DDL, expand-contract, `CREATE INDEX CONCURRENTLY`, a CI lint on dangerous statements, and replaying every migration on an empty database as a merge gate [T3, RAITHub, *Database Migration Broke Production?*].

### 5.4 Temporal bugs: leakage of future information into past-state views

The most insidious failure is a past-state view that quietly reads the future. Controlled backtest experiments isolate the mechanisms: centered rolling windows and same-day-open execution with post-open data "cause large and stable increases in both predictive and trading metrics," while global normalization and same-day-close execution are weaker — so the dominant leak is a feature whose *availability* exceeds the decision epoch [T1, *When Alpha Disappears: A One-Switch Benchmark for Decision-Time Leakage* (arXiv:2605.23959), Abstract]. A formal treatment proves look-ahead-freedom is temporal non-interference, and on any pipeline language where "a datum's availability may depend on data values" it is undecidable (Π¹₀-hard) — leakage is detectable but freedom cannot be certified by silence [T1, *Look-Ahead-Freedom as Temporal Non-Interference* (arXiv:2607.04958), Abstract and Theorem 1]. The practical tests are mechanical: mutate the future and re-run the pipeline; if past features change, they leaked [T3, GitHub, *prakulhiremath/temporal-leaks*], and static linters flag `shift(-n)`, `rolling(center=True)`, backfill, and fit-before-split [T3, GitHub, *saksham10arora-dotcom/backtest-guard*]. The consequences are large: a model extracting half the signal "already gains 75% of the full-memorization inflation" [T1, *Temporal Leakage in LLM Backtesting* (arXiv:2608.02985)].

### 5.5 What holds up

Across every incident category, the same practices survive: **bitemporal record-keeping** (both clocks append-only, so corrections never overwrite original records); **point-in-time stamping by availability date** rather than fiscal-period date; **hash-based change detection** with half-open effective ranges and a far-future sentinel [T2, datamodelassistant.com]; **weak schema plus forward-only versioned events with upcasters**, never a rename [T1, Overeem et al., 2021; T3, Boyko]; **expand-contract migrations** with idempotent, verified, gated destructive steps [T3, Graph Data Modeling; T3, RAITHub]; **snapshots derived-from and disposable-to the event log** [T3, DEV Community]; and **availability-separated pipelines** that make look-ahead-freedom checkable [T1, arXiv:2607.04958]. The through-line: history should be cheap to *write* correctly and expensive to *edit* — every system that let history be edited in place eventually lost the ability to explain what it knew and when.
