# From SaaS funnel to open-source project

**Status:** research complete, no code written yet
**Date:** 2026-11-24
**Scope:** what in BAM is shaped by the "three paid tiers, self-serve signup,
hosted connectors" assumption, and the smallest set of changes that makes it a
credible self-hosted open-source project — without giving up the tenancy
isolation that the app depends on.

---

## 1. Audit: what is SaaS-shaped today

Every line below was read in the working tree at `main` (`f20489e`).

| SaaS surface | Where | Size / coupling |
|---|---|---|
| Marketing site + pricing funnel | `mvp/ui/templates/marketing.html` | 766 lines; `<a href="#pricing">`, hero copy, five-specialist pitch; rendered by `index` for logged-out visitors and by `signup` on GET |
| Self-serve signup | `mvp/ui/app.py:329` `signup()` | provisions tenant → creates user → `plan="free"`; rollback path on duplicate email |
| Plans, quotas, usage metering | `mvp/plans.py` | 295 lines, own `data/usage.db`, `PLANS` is the copy source for pricing; enforced at 2 call sites (`app.py:1215` arbiter, insights) |
| Quota status in API | `app.py:1027` `/api/plan`, `:1215` `plans.consume` | cheap to gate |
| Default admin identity | `mvp/auth/store.py:280` | `BAM_ADMIN_EMAIL` defaults to `jon@jonco.local` |
| Dev-machine env loading | `mvp/ui/app.py:13-18`, `mvp/insights.py:98-112` | reads `~/.hermes/.env` by absolute path and falls back to `~/.hermes/config.yaml` for the LLM key — never true for anyone cloning the repo |
| Hosted integration proxy (paid SaaS) | `mvp/integrations/nango.py` | 13 provider specs all resolve through Nango; `NANGO_SECRET_KEY` gates everything |
| Hosted LLM | `mvp/insights.py:98` | `OPENROUTER_API_KEY`; without it `call_llm` returns a "no key" error payload rather than raising, but the UI shows empty hypotheses instead of a first-run prompt |
| Single-file registry + tenant dirs as templates | `data/tenants.json`, `provisioning._clone_template` clones `data/<template>` | demo tenants double as starter templates; runtime state and examples share one directory |
| No licence / community files | repo root | no `LICENSE`, `CONTRIBUTING`, `SECURITY`, CI, Dockerfile, `pyproject.toml`; GitHub description "business as machine ", zero topics |
| README | `README.md` | still describes the single-tenant JonCo MVP pipeline; predates tenancy, interview, graph chat |

**What is already open-source-shaped, and should not be rebuilt:**

- Filesystem-first data. Graphs are rebuilt from JSON on every request
  (`loader.load_graph`), so a workspace is a directory a human can read and diff.
- `mvp/types.py` + `data/types.json` — business types are already a user-extensible
  registry with `register()`/`load_custom_types()`.
- `mvp/specialists/` — specialists are plain modules with a base class, not a plugin
  framework.
- `conftest.py` bridges the script-style `check()` harnesses into pytest:
  **448 tests pass in 3.4s** (`uv pip install pytest && pytest -q`), so CI is a
  workflow file, not a test rewrite.
- Honest degradation: missing `NANGO_SECRET_KEY` reports "not configured" instead
  of failing; the same pattern should cover every credential.
- No telemetry, no phone-home, no proprietary data formats.

## 2. Target shape

One sentence: **single workspace by default, many by configuration; no funnel, no
billing, no hosted dependency required to get value.**

The security invariant does not move. Tenancy remains the authorization
boundary in both editions — a user may only touch tenants in
`auth.current_user.tenants` (`_current_tenant`, `auth.current_tenant`,
`tenancy.require_tenant`), and `test_tenancy.py` (30/30) stays the gate. "Less
SaaS" means removing the *commercial* surface, not weakening isolation: a
self-hoster running two workspaces needs exactly the same guarantee.

Introduce one switch, `BAM_EDITION` (`oss` | `cloud`, default `oss`), resolved in
a single module. Every commercial behaviour reads that module. No forks, no
build-time templating, no duplicate code paths.

### Edition table

| Behaviour | `oss` (default) | `cloud` |
|---|---|---|
| `/` logged out | login page + "what this is" panel, link to docs | marketing site |
| `/signup` | 404 | open |
| `/pricing` | absent (already a fragment of `marketing.html`) | present |
| Plans / quota | module inert; `consume()` returns immediately; no `usage.db` writes | enforced |
| First admin | `/setup` wizard on empty user table | env-seeded admin, invite flow |
| Nango | optional; connectors say "not configured" | expected |
| LLM | optional; deterministic output otherwise | expected |

## 3. Phases

Ordering is deliberate: hygiene first (a cloner must be able to run the thing),
then de-SaaS, then packaging, then the data path that makes it useful to a
stranger. Each phase ends green on the same command.

### Phase A — repo hygiene (≈ half a day)

- **A1. `LICENSE`** — pick before anything else (decision in §6). Add SPDX
  identifier to `pyproject.toml` when it lands in C1.
- **A2. `SECURITY.md`** — supported versions, private reporting address, and the
  one real caveat: `BAM_DEBUG=1` on a public host is RCE, already documented in
  `.env.example`.
- **A3. `CONTRIBUTING.md`** — `uv venv`, `uv pip install -r requirements.txt
  pytest`, `pytest -q`, how to add a business type (`data/types.json`), how to add
  a specialist (`mvp/specialists/`), and the rule that a new graph field needs a
  loader default so old workspaces keep loading.
- **A4. `CODE_OF_CONDUCT.md`** — Contributor Covenant 2.1 verbatim.
- **A5. `.github/`** — `workflows/ci.yml` (uv + `pytest -q` on 3.11/3.12),
  `ISSUE_TEMPLATE/bug_report.yml`, `PULL_REQUEST_TEMPLATE.md`.
- **A6. `README.md` rewrite** — three commands to a running graph, one screenshot,
  "what it is / what it is not", pointer to `docs/`. Move the JonCo MVP narrative
  into `docs/example-coffee-shop.md`; it is still the best explanation of the graph.
- **A7. Env loading** — replace the absolute `~/.hermes/.env` block in
  `mvp/ui/app.py` and the `~/.hermes/config.yaml` fallback in
  `mvp/insights.py:98-112` with `python-dotenv` if installed, else nothing;
  document `BAM_*` variables in `.env.example`. Removes two developer-machine
  assumptions that will otherwise confuse every first contributor.
- **A8. GitHub metadata** — description ("Model a business as a transformation
  graph…"), topics (`business-intelligence`, `graph`, `agents`, `flask`,
  `self-hosted`), homepage, enable Discussions.

**Proof:** fresh clone in `/tmp`, `uv venv && uv pip install -r requirements.txt
pytest && pytest -q` → 448 passed; `python -m mvp.ui.app` serves `/health`.

### Phase B — de-SaaS the app (≈ 1 day)

- **B1. `mvp/edition.py`** — reads `BAM_EDITION`, exposes `EDITION`, `is_cloud()`,
  `is_oss()`; validates the value and fails loudly on a typo.
- **B2. Route guards in `mvp/ui/app.py`** — `signup()` and the logged-out branch of
  `index()` consult `is_cloud()`; in `oss`, `/` renders the login page and
  `/signup` returns 404 via `abort()`. `marketing.html` stays in the tree (it is
  the cloud edition's front door) but no `oss` request reaches it.
- **B3. Plans inert in `oss`** — `plans.consume()` and `plans.status()` short-circuit
  when `is_oss()`. Keep the module: deleting it would fork the request path, and
  metering is still the correct design for `cloud`. `provisioning.provision_tenant`
  stops defaulting new workspaces to `"free"` in `oss` (no plan row at all).
- **B4. `/setup` first-run wizard** — new `mvp/setup.py` with `needs_setup()` and
  `create_first_admin()`; route renders a template that asks for email, password
  (≥12), display name, and one workspace (name + business type). Registered as a
  public endpoint alongside `auth.login`/`auth.health`. When
  `BAM_ADMIN_EMAIL`/`BAM_ADMIN_PASSWORD` are set the env path still works — that is
  the headless/automation route, and it must not fall back to `jon@jonco.local`.
- **B5. Single-workspace ergonomics** — a user with one membership never sees a
  picker: `auth.current_tenant()` already resolves it; assert it in a test rather
  than adding UI.
- **B6. `test_edition.py`** — script-style like its neighbours: `oss` has no
  `/signup` (404), `/` unauthenticated is the login page, `/setup` exists on an
  empty user table and 404s once a user exists, `plans.consume` does not write
  `usage.db`, and `cloud` still shows marketing at `/`. Add a tenancy isolation
  assertion that runs in both editions.

**Proof:** `pytest -q` → 448 + new checks green; `BAM_EDITION=cloud pytest -q` →
same suite, cloud branch exercised; manual pass of `/setup` on a scratch
`BAM_DATA_DIR` produces no default admin and no `usage.db`.

### Phase C — self-host packaging (≈ 1 day)

- **C1. `pyproject.toml`** — project metadata, deps mirroring `requirements.txt`,
  optional extra `dev = pytest`, console script `bam = mvp.cli:main`. Keep
  `requirements.txt` as the pinned install path for Docker; one source of truth for
  versions is `pyproject.toml` and `requirements.txt` is generated from it.
- **C2. `mvp/cli.py`** — `bam serve [--host --port --data-dir]`, `bam workspace
  list`, `bam workspace new <slug> --type cafe`. Deliberately not a plugin system:
  three verbs that wrap code paths that already exist.
- **C3. `Dockerfile`** — `python:3.12-slim`, non-root user, `gunicorn` as the
  server (the Flask dev server stays a dev tool), `HEALTHCHECK` against `/health`,
  `VOLUME /app/data`.
- **C4. `compose.yaml`** — one service, `./data:/app/data`, `.env` optional,
  port 8080, healthcheck inherited.
- **C5. `Makefile`** — `make test`, `make run`, `make docker`.
- **C6. `docs/self-hosting.md`** — docker path, bare-metal path, `BAM_*` reference,
  backup = copy `data/`, upgrade = pull + restart (no migrations yet, JSON contract
  is stable), and the honest limits section.

**Proof:** `docker compose up` on a clean host, `/setup` completes, a workspace is
imported from `examples/`, graph renders; `docker compose down -v` leaves no
residue.

### Phase D — a data path a stranger can use (≈ 2 days)

This is the largest real gap: today a workspace is only useful if you already have
JSON in the shape `data/jonco/` has.

- **D1. `docs/workspace-format.md`** — the contract: `company.json` plus optional
  `transactions.json`, `payroll.json`, `cogs_purchases.json`, `overheads.json`,
  … keyed to the canonical field registry in
  `mvp/multiagent/data_gaps.py` (10 keys). Anything absent must degrade to a gap
  report, not a crash — `DataGapAnalyzer` already models this.
- **D2. `bam import <workspace> <csv|json>`** — maps columns to canonical fields,
  writes the workspace files, then runs `load_graph` as its own verification step.
  Column mapping via a small explicit table per business type, not a guessing
  engine.
- **D3. Nango stays optional** — document the three choices (local files, keyed
  Nango cloud, self-hosted Nango) and keep the "not configured" degradation that
  `integrations/nango.py` already implements.
- **D4. `examples/`** — move the two demo workspaces (`kaf` café, `athlete-life-ltd`
  partial-onboarding example) out of `data/` into `examples/`, and point
  `provisioning._clone_template` at it. Runtime state and shipped examples stop
  sharing a directory; `data/` becomes purely local (already mostly ignored).

**Proof:** `bam workspace new demo --type cafe && bam import demo ~/sales.csv`
produces a loadable graph and the dashboard renders with the gap report showing
exactly what is missing.

### Phase E — launch readiness (≈ half a day)

- **E1. Version + tag** — `__version__`, `CHANGELOG.md`, `v0.1.0`, GitHub release
  with the docker command in the body.
- **E2. Docs index** — `docs/README.md` linking quickstart, workspace format,
  self-hosting, architecture, and the two existing research plans.
- **E3. Launch checklist** — pinned "Roadmap" issue, Discussions enabled, topics,
  social preview image, and the explicit statement that there is no telemetry and
  no hosted service to upsell.

## 4. Order, effort, and what each phase unlocks

| Phase | Effort | Unlocks |
|---|---|---|
| A hygiene | 0.5d | a stranger can clone, run tests, and know the licence |
| B de-SaaS | 1d | the product reads as a tool, not a storefront |
| C packaging | 1d | `docker compose up` |
| D data path | 2d | a stranger's own numbers |
| E launch | 0.5d | something worth posting |

A and B are the minimum credible cut: hygiene alone leaves a storefront, de-SaaS
alone leaves an un-runnable repo.

## 5. Invariants, risks, rollback

- **Tenancy isolation** is untouched by every phase; `test_tenancy.py` must stay
  30/30 in both editions.
- **No default credentials.** `jon@jonco.local` disappears in Phase B; `/setup` or
  env seeding only. This is a security change, not cosmetic.
- **Secrets in the working tree.** `data/.secret_key`, `data/initial_admin_password.txt`
  and `.env` are gitignored — verify with `git check-ignore -v` before the first
  public push, and confirm none were ever committed (`git log --all -- data/.secret_key`).
- **Compatibility.** `data/tenants.json` is read on every request; Phase D moves
  *examples*, not the registry, so existing workspaces keep loading. Any registry
  schema change needs a read-time default, never a migration script.
- **Rollback.** `BAM_EDITION=cloud` restores today's behaviour exactly; every
  Phase B change sits behind that flag, so a bad release is one env var from the
  previous product.
- **Risk: scope creep into plugins.** Resist a connector SDK, a template DSL, a
  theme system. The extension points that already exist (`data/types.json`,
  `mvp/specialists/`, JSON workspaces) are the ones to document.

## 6. Decision needed

`LICENSE` blocks Phase A and is not reversible in practice once people fork.

- **AGPL-3.0** — best fit for a product whose value is the running service;
  protects against a hosted clone; deters some corporate contributors.
- **Apache-2.0** — maximum adoption, patent grant, permissive; a competitor may
  host it commercially.
- **MIT** — simplest, most permissive, weakest protection.

Recommendation: **AGPL-3.0** if the intent is "self-host it, or pay someone to run
it"; **Apache-2.0** if the intent is "get it used and contributed to, ignore
hosting upside".
